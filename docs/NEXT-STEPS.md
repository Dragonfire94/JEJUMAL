## A. 콘텐츠 정합성 트랙 — 남은 일 (우선순위 순)

### A-1. 예문 655개 채우기 — 제일 중요

2025년 제주학연구센터 기본어휘에서 새로 들어온 단어 대부분(989개
중 약 598개, 유닛 배치 대기 57개 포함 총 655개)이 **단어와 뜻만
있고 예문이 없다.** 책 자체에 예문이 없어서, 지어낸 문장을 넣는
대신 비워둔 상태다.

- 참고 자료: 각 lexeme의 `bookMeta.definition`(책 원문 뜻풀이),
  `bookMeta.otherJejuForms`(다른 표기 변이형)
- 지켜야 할 원칙(이 프로젝트에서 계속 지켜온 것): 예문을 지어낼 땐
  `review.naturalness: "provisional"`로 명시하고, 검증 안 된 걸
  검증됐다고 표시하지 않는다. 가능하면 AI Hub 말뭉치(`data/aihub/`)에
  실제 그 단어가 쓰인 문장이 있는지 먼저 찾아보고, 없으면 사람이
  최종 검수할 걸 전제로 작성한다.
- 작업량이 크므로 한 번에 다 하지 말고, 이미 유닛에 배정된 598개부터
  우선(화면에 바로 노출되는 것들이라 효과가 큼).

### A-2. PUA(옛한글 표기 깨짐) 39개 마무리

`data/jeju-basic-vocab-2025/pua-glyph-mapping.json`에 아직
`confidence`가 `medium`(16개)이거나 `low`(7개)인 글자가 있다.

- medium 16개: 모양+뜻은 통하는데 확증까지는 못한 것들 — 자체
  사전(`data/dictionary/jeju_dialect_full.json`)·말뭉치와 다시
  대조해보면 몇 개는 더 확정할 수 있을 것으로 보인다.
- low 7개: 여러 번 봐도 애매해서 사람(실제 화자나 국어사 전문가)
  판단이 필요하다. `data/jeju-basic-vocab-2025/pua-low-review-7.png`에
  실제 PDF 크롭 이미지가 정리돼 있으니 그걸 보여주면 된다.

### A-3. 유닛 미배치 57개 배치

랭크 시스템(`src/lib/units.ts`)이 "테마 10개 × 유닛 10개" 정확히
100유닛 그리드에 고정돼 있어서, 지금 배치 못한 57개(형용사·감탄사
위주)를 넣으려면 이 그리드 자체를 어떻게 늘릴지 먼저 정해야 한다.
두 방향이 있다:

1. 기존 10개 테마 각각을 유닛 11개, 12개... 로 늘리기 (랭크 승급
   기준값도 같이 조정 필요)
2. 11번째 테마를 새로 만들고 랭크/웨이브 구조 자체를 재설계

`same_meaning_different_form 정리` 라운드에서 유닛 크기를 8~10개로
유연하게 만든 전례가 있으니, 완전히 새로 설계하기보다 그 위에서
확장하는 게 자연스러울 수 있다.

### A-3.5. 2025 기본어휘 stable ID 마이그레이션 — 3B-1B까지 완료

`docs/basic-vocab-2025-stable-id-design.md`(3A) → `docs/basic-vocab-2025-stable-id-production.md`(3B-1A) →

남은 순서:

- 3B-2: B(42건) 중 `bookMeta.posLabel` 자체가 틀렸던 18건은 이미
  고쳤다. 나머지 24건은 `posLabel`은 이미 맞았고 앱 `partOfSpeech`
  스키마에 의존명사/관형사 카테고리가 없어서 근사(noun/adjective)한
  게 원인이다 — 카테고리를 신설할지 근사를 유지할지 정책 결정 필요.
- 3C: 신규 71개 중 실제 앱 핵심 단어로 넣을 것 개별 선별

## B. 제품/UX 트랙 — 먼저 확인부터 해야 함

`product-improvement-plan.md`의 P0~P5 로드맵(7절)은 두 건의 외부
감사를 검토하고 짠 계획인데, **체크리스트가 실제 코드를 못 따라간
것으로 보인다.** 이번에 문서를 정리하면서 코드를 잠깐 훑어봤더니:

- `conceptId` 기반 동의어 오답 제외(P0-1) → `src/lib/quiz.ts`에
  `conceptId()` 함수로 이미 구현돼 있음
- `hasAudio` 체크로 음원 없는 듣기 문제 제외(P0-3) → `quiz.ts`에
  이미 필터링 있음
- `reviewStatus`/`blocked` 단어 빌드·퀴즈 제외(P0-2) → 스키마와
  `quiz.ts`에 이미 있고 테스트(`blocked words never appear in a
  lesson`)까지 있음
- 복습 간격 `dueAt` 게이팅(P0-4) → `src/lib/progress.ts`에 주석으로
  "예정일에 도달한 경우에만 승급" 로직 확인됨

**즉 P0(출시 전 필수) 항목 대부분이 이미 구현된 것으로 보이는데
체크박스는 전부 `[ ]`로 남아있다.** 이 로드맵을 실행하기 전에:

1. P0/P1/P2 각 항목을 코드에서 실제로 다시 확인(재감사)해서 체크리스트를
   현재 상태에 맞게 갱신한다.
2. 그 다음에야 "진짜 남은 게 뭔지" 알 수 있다 — 지금 상태로 로드맵을
   그대로 따라가면 이미 끝난 일을 다시 할 위험이 있다.

이 재감사 자체가 다음에 할 일 중 하나다.

### B트랙 작업 방식 — 모듈별 브랜치 + PR로 전환 (결정됨)

콘텐츠 트랙(A)은 지금처럼 한 브랜치(`claude/jeju-dialect-education-feedback-2dtss7`)에
계속 커밋을 쌓는 방식을 유지한다. **B트랙은 다르게 간다** — 사용자와
합의된 방식:

1. B트랙 항목(재감사 결과 실제로 남은 것으로 확인된 것)마다 **새 작업
   브랜치**를 판다(예: `claude/quiz-duplicate-answer-fix`).
2. 모듈 하나가 완성되면 **Pull Request**를 만들어 리뷰할 수 있게 한다
   (지금까지처럼 같은 브랜치에 바로 push만 하고 끝내지 않는다).
3. 사용자가 PR을 보고 로컬에서 테스트한 뒤 병합(merge) 여부를 결정한다.
4. 재감사 자체는 코드를 안 고치는 조사 작업이라 지금 브랜치에서 문서로
   남기고, **실제 코드 변경이 필요한 항목부터** 이 새 방식을 적용한다.

이렇게 정한 이유: A트랙은 콘텐츠 데이터 작업이라 "모듈" 단위가 잘
안 맞지만, B트랙(퀴즈 로직·복습 알고리즘 등)은 기능 단위로 쪼개기
좋고, PR 리뷰를 거치면 이미 구현된 걸 다시 만드는 실수(위에서 발견한
문제)도 더 잘 걸러진다.
